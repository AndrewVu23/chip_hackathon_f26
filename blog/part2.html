The kill test

We built the harness, wrote the gates, and ran the one experiment designed to end the project early. It fired. Here is what the number actually said — and the narrower, real gap it pointed at instead.

The baseline's measured pattern — 32 all-bank commands at M1 = 0.75  ·  blue = row already open  ·  amber = full tRC row cycle paid
0x10

The bet, restated

Part I established the collision. Production serving scatters the KV cache into fixed-size pages; a PIM attention unit only goes fast when it can activate the same row index in every bank of a channel at once. This part is the measurement.

The proposal made a falsifiable claim: under realistic paged allocation, an all-bank PIM unit lands in an already-open row only rarely, and a smarter allocator recovers most of the loss. The brief attached a stop rule to it, in writing, before any code existed:

Phase 0 — the kill test. Minimum viable path: steady workload + vLLM-semantics paged allocator + HBM3-PIM address map + M1 only. Produce one number. If M1 is under ~0.3, the premise holds. If M1 is over ~0.7, stop and say so immediately. Do not rationalize the number or go looking for a workload that makes it look bad.

That rule exists because the failure mode of a two-week architecture project is not being wrong — it is spending ten days making a dead hypothesis look alive. So the very first runnable configuration was the one most likely to kill the project.

It came back at M1 = 0.970. The stop rule fired on day one of measurement, and the honest answer to "did the premise survive?" is not as stated. The rest of this page is what we found when we looked at why.

0x11

What we built to measure it

Six Python modules, no GPU, no inference, no RTL. The whole pipeline runs single-threaded on a laptop in under a minute per configuration, which is the only reason the kill test could happen before the harness was "finished".

workload.pyDeterministic request streams. steady: Poisson arrivals at 0.25 req/step, ShareGPT-like lognormal prompt and output lengths (median ~200 tokens each, long tail). longctx: 8k–32k prompts, short outputs. Same seed, same stream, always.
↓ requests (arrival step, prompt_len, output_len)
sim.pyContinuous-batching decode loop. One step = one engine iteration: FCFS admission with an oracle capacity check, one token appended per running sequence, a new block allocated on each block-boundary crossing, blocks released on completion. Metrics sampled every 16 steps across 8 running sequences.
↓ block tables (which physical block holds which 16 tokens)
allocator.pypaged is a port of vLLM v0.2.7 BlockAllocator — free list initialised ascending, allocate() pops from the tail (LIFO), free() appends. contiguous is the oracle upper bound: one physical span per sequence, reserved whole. random is the worst-case anchor.
↓ block ids → linear burst addresses
addrmap.pyPure bit-slicing from a linear KV address to (channel, bank_group, bank, row, column). Three interleaving schemes, exactly invertible, tested before it was written.
↓ per-burst DRAM coordinates
pimmodel.pyPer channel, coalesce the burst stream into all-bank commands (same row, distinct banks) inside a 64-burst controller reorder window, then compute M1–M4.

The one decision that made this cheap

The brief forbade running vLLM. Installing it on an Apple Silicon laptop is a multi-day tax, and we do not need inference — we need allocation event streams. So we ported the allocation policy out of vllm/core/block_manager.py at commit 2e0b6e7 and cited it in the docstring, line by line.

One consequence of that port is worth keeping in your head, because it shapes every number below: vLLM's free list is a LIFO stack initialised in ascending order, so a fresh pool hands out block ids in descending order. Even the very first sequence is reverse-ordered in physical space — and, more importantly, it is still a run of consecutive ids. Paged allocation is not random allocation. That distinction turns out to be most of the story.

Fidelity gap, logged. Real vLLM frees a finished sequence by iterating set(block_table) — unordered. We free in block-table order for determinism (gate 4). That slightly tidies the baseline's free list, so if anything it flatters the paged baseline we are trying to indict.
0x12

Four metrics, frozen before the first run

The brief fixed these definitions and forbade changing them without sign-off. That constraint is what makes a surprising result reportable instead of negotiable.

MetricDefinition
M1Row-hit rateFraction of all-bank commands whose target row is already open. All-bank semantics are strict: a partial hit is a miss, because a command at a different row re-activates every bank.
M2Bank-parallelism utilisationParticipating banks per command ÷ banks per channel. A command that only feeds 2 of 16 banks wastes 14 MAC units.
M3Effective PIM bandwidthBW_ideal × M2 × tCCD_ab / (M1·tCCD_ab + (1−M1)·tRC) — hits cost one column interval, misses cost a full row cycle.
M4Decode-step latencykv_bytes_touched / M3, in ns, for the attention portion of one layer.

Only one timing quantity is load-bearing: the ratio tRC / tCCD_ab. We set it to 45 ns / 4.3 ns ≈ 10.5, from the published AttAcc/Ramulator 2 measurement that nRC runs 10–11× nCCDAB for decode GEMV. Absolute nanoseconds are indicative until a Ramulator cross-check runs.

The geometry everything hangs on

HBM3-PIM preset: 32 pseudo-channels × 16 banks × 1 KB rows × 32 B bursts. One all-bank command therefore moves 16 × 32 B = 512 B, and one row index across all 16 banks of a channel — a row-group — is 16 KB. Ideal all-bank bandwidth is 3810 GB/s.

The model shape is Llama-3-class GQA: 8 KV heads × 128 dim × fp16 = 4096 B of K+V per token per layer. So a 16-token block is 64 KB, which — spread across 32 channels — is a 2 KB slice per channel. That is one eighth of a row-group. Hold onto that fraction; it is the root of every number in this article.

Run the same arithmetic backwards and you get the block size the hardware actually wants: one full row-group in every channel is 1024 × 16 × 32 / 4096 = 128 tokens. The code computes it rather than hardcoding it (config.derive_block_tokens). The serving community converged on 16.

0x13

The hidden variable: the address map

We went in thinking the allocator was the independent variable. It is not the only one. The memory controller's interleaving scheme decides, before the allocator gets a vote, whether scattered placement even matters.

Each scheme is a bit layout over a 28-bit linear burst address. Read these right-to-left, LSB first — the field sitting on the low bits is the one that changes as you walk consecutive addresses.

The layouts below are the ones the harness actually implements. If bit patterns are not how you think, skip to the grid underneath them — it walks a real block through each map and shows you where the bursts land.

host-centric  ro : bg : ba : ch : co
row [27:14] bg ba ch [9:5] col [4:0]

The map named in the brief. All 5 column bits are lowest, so inside one channel a contiguous stream sweeps an entire row of one bank before it ever touches the next bank. Rows stay wide open. Bank parallelism dies.

host-cacheline  ro : co_hi : bg : ba : ch : co_lo
row [27:14] col_hi bg ba ch [5:1] c

What a real memory controller does: interleave 64 B cachelines across channels, then put the bank bits immediately above them to maximise bank-level parallelism for scattered host traffic. Banks interleave beautifully. Rows now fragment with placement.

pim-friendly  ch : ro : co : bg : ba
ch [27:23] row [22:9] col [8:4] bg ba

Bank bits lowest: 16 consecutive bursts land in 16 distinct banks at the same (row, column) — exactly one all-bank command. Each channel owns one huge contiguous slab. This is what PIM-attention papers assume, and it is not what hosts do.

rowcolumnchannelbank / bank-group

The two host maps fail PIM in opposite directions. host-centric keeps rows open and destroys bank parallelism. host-cacheline keeps banks busy and lets rows fragment. A project that had only measured M1 would have seen the first configuration as healthy.

Five gates before any number counts

49 pytest tests, all green, including the five validation gates the brief required. Two of them did not pass as literally written, and the honest version of each is worth more than the clean version.

GateRequiredResult
1Perfect-case anchorcontiguous + pim-friendly map ⇒ M1 ≥ 0.95pass — measures 0.969, which is exactly 1 − 1/32: one ACT per row-group, then 31 hits. That is the geometric ceiling for 1 KB rows and 32 B bursts, so 0.95 is the right bar.
2Worst-case anchorrandom placement ⇒ M1 ≈ 1/rows within 2×pass, reinterpreted — see below.
3MonotonicityM1 non-decreasing in block size, contiguous allocatorpass — but it degenerates: a contiguous span is contiguous at any granularity, so M1 is essentially block-size-invariant here. The gate really only proves no aliasing bug makes it decrease.
4Determinismsame seed ⇒ byte-identical CSVpass
5Conservationallocated − freed == live, every step, every policypass — asserted inside the allocator every step

Why gate 2 needed a footnote

The gate says random placement should drive M1 down to roughly 1/rows_per_bank = 1/512 for the test geometry. Two things get in the way, and both are real behaviour rather than bugs:

  1. A coalescing controller merges away the very coincidences the heuristic counts. When two adjacent bursts happen to share a row, a windowed controller folds them into one command instead of scoring a hit. So the strict factor-of-2 check runs on a single-bank stream, where merging is impossible and every burst is its own command. There it lands within 2× of 1/512. ✓
  2. With random banks and a 64-burst window, coincidental same-(row, bank) pairs legitimately produce ~3/rows. That is bounded as a looser secondary check (≤ 8/rows) rather than hidden.

Both are documented in the test docstring and flagged to the owner, because the brief explicitly said not to reinterpret a gate silently. A gate you quietly loosen is not a gate.

Verdict per the brief's stop rule

STOPPED. The rule was: M1 > 0.7 ⇒ stop and tell the owner. Baseline M1 is 0.970 on the brief's host-centric map and 0.759 on the realistic one. Neither is "under 0.3". Reported as measured, no rationalising, no hunting for a workload that makes it look worse.

The premise as written — "paged allocation destroys the row-hit rate" — did not survive contact with the harness. What survived is narrower, and it is real.

What the runs actually show

  1. The brief's baseline loses its 10× through the wrong metric. host-centric gets 9.7% of ideal bandwidth with a healthy M1 of 0.97. The damage is entirely M2 = 0.124 — whole-row-per-bank sweeps serialise the banks. With a 64-burst window touching 2 of 16 banks, 2/16 = 0.125. The measurement lands on the arithmetic. The kill criterion was aimed at the wrong number for this map.
  2. Under the pim-friendly map, paged ≡ contiguous. Both hit 0.969 / 1.000 / 2938 GB/s — identical to three decimal places, because a 16-token block there is four whole row-groups inside one channel. Scatter is harmless. No allocator story exists in that regime at all.
  3. The recoverable gap lives in exactly one place: where a block's per-channel slice is smaller than a row-group. At 16 tokens that slice is 2 KB against a 16 KB row-group, and there paged (0.759 / 1173 GB/s) versus contiguous (0.958 / 2719 GB/s) is 2.3× from placement alone.
0x16

Why those exact numbers

0.970, 0.124, 0.759, 0.969. None of these are empirical accidents. Every one falls out of the bit layout, and once you see the rule you can predict the whole sweep before running it.

Take the host-cacheline map. A 16-token block is 64 KB of contiguous linear address space, or 2048 bursts — bits 0 through 10. The row field starts at bit 14. So an entire block sits inside one row index, and it needs

// commands one block costs, per channel
block_bytes / channels / (banks × burst_bytes)
  = 65536 / 32 / (16 × 32)
  = 4 commands   — all at the same row

Four commands, one ACT, three hits. M1 = 3/4 = 0.75. The measured value is 0.759; the extra 0.009 is the LIFO free list occasionally handing out two adjacent block ids in a row. That is the whole result.

Generalise it. For scattered blocks whose neighbours share no row:

M1 ≈ 1 − 1/k,   where k = block_tokens × kv_bytes_per_token / (channels × banks × burst_bytes) is the number of all-bank commands one block costs per channel — capped at 1 − 1/cols_per_row = 0.969 once a block covers a whole row-group.

For this configuration k = block_tokens / 4:   16 tokens → 0.750  ·  32 → 0.875  ·  64 → 0.938  ·  128 → 0.969.

And the two block-size probes we ran (500 requests, seed 0, paged, host-cacheline) land on it:

At 4 tokens the block's per-channel slice is 512 B — exactly one all-bank command — so the "hits after the first ACT" term vanishes and the law would predict zero. It measures 0.571 instead, because at that granularity the 64-burst reorder window spans four consecutive blocks and the LIFO free list keeps handing out consecutive ids. M2 also falls to 0.566: there is no longer enough of a block in one channel to spread across 16 banks. Below the row-group boundary, both mechanisms degrade at once.

0x17

The cost of the upper bound

One number in the run logs is easy to skip past and shouldn't be: the contiguous allocator — our "ideal" reference — failed to place a request 9,162 times over the same 2000-request stream.

The paged baseline had zero placement failures. Contiguous had nine thousand, and needed 12,148 engine steps to drain the same workload against paged's 10,782 — about 13% more wall-clock decode iterations for identical work, purely from head-of-line blocking while it waited for an extent big enough.

This is not a bug in the reference implementation; it is the reason PagedAttention exists. Any "PIM-aware allocator" that reaches its bandwidth by demanding contiguity has simply moved the cost from the memory controller to the scheduler. Whatever Phase 2 builds has to beat 1173 GB/s without reintroducing 9,162 admission stalls — and that constraint was not visible from the proposal.

Read the reference implementation's failures, not just its metrics. The upper bound is only an upper bound on the axis you were measuring.
0x18

The open decision

Phase 0 ends at a fork the measurement cannot resolve on its own. Both branches are honest; they tell different stories with the same CSVs.

A · Keep the allocator framing
headline: placement is worth 2.3×

Report the original claim with the honest numbers: on a realistic channel-interleaved map, paged placement costs 2.3× effective PIM bandwidth against contiguous, and a PIM-aware allocator should recover most of it without contiguity's admission stalls.

Risk: the gap is narrower than the proposal implied, and it only exists under channel-interleaved maps. Upside: the fix is still the contribution, and spec may widen the gap considerably.

B · Reframe around geometry
headline: block size 16 is the wrong constant

Lead with the block-size × address-map result: a PIM-backed serving system should use the derived 128-token block, not 16, and that single change moves 1173 → 2795 GB/s. The allocator becomes the second lever, applied where blocks still land below a row-group.

Risk: "use bigger pages" is a smaller contribution than a new allocator, and bigger blocks cost internal fragmentation we have not yet measured. Upside: it is the finding the data most strongly supports.

Note that block size 16 → 128 buys 2795 GB/s and placement alone buys 2719 GB/s — the two levers land in nearly the same place, which means they are attacking the same underlying quantity: how much of a row-group a single allocation unit covers. That is an argument for framing B being the more general statement, and for A being the interesting special case once blocks are already small for capacity reasons.

0x1A

Limitations, stated rather than approximated

Each of these is a place the model diverges from real hardware or real vLLM. Where a simplification has a direction, the direction is noted — most of them are conservative against the project's own claim.

  • We model vLLM's allocation policy, not vLLM. Ported and cited to file, commit, and line. Free order is block-table order rather than vLLM's unordered set() iteration, which slightly tidies the baseline's free list.
  • One representative layer. vLLM keeps one KV tensor per layer but a single block table per sequence, so every layer sees identical inter-block placement. M1/M2 generalise; absolute bytes and M4 scale with layer count.
  • Within-block layout is assumed PIM-optimal. The accelerator writes K/V at decode time and can arrange bytes inside a block however it likes; the allocator only controls which physical blocks. That is the correct abstraction boundary for an allocator study, and it means co-designed within-block layouts could shift absolute numbers without changing the comparison.
  • Column-relaxed all-bank commands. We require one row and distinct banks, but not one broadcast column — real HBM-PIM broadcasts a single column. Relaxing this can only help the scattered baseline, so it is conservative for our claim.
  • Oracle admission control. Final lengths are known and a request is admitted only if its whole footprint fits. This removes watermarks, preemption, and swapping from scope. It is identical across policies, so comparisons stay fair — but real preemption would churn the free list harder, meaning the baseline shown here is the gentle version.
  • Open-row state starts cold per sampled sequence. Batch interleaving between sequences is not modelled; the cost is at most one extra miss per channel per sample.
  • Controller reorder window is a parameter, not a tuned constant. 64 bursts per channel by default; --coalesce inorder is the pessimistic end. It is a sensitivity axis for Phase 2, not a knob we turned until the answer looked good.
  • Absolute nanoseconds are indicative. Only the tRC/tCCD_ab ≈ 10.5 ratio is load-bearing, pending the Ramulator cross-check.
  • Channel-level load balance is out of scope. M1–M3 rate per-command quality. They say nothing about whether all 32 channels stay busy.

0x1B

Where Part III picks up

Phase 0 was supposed to produce a motivating figure. It produced a fork in the road and three findings instead, which is a better return on two days.

  1. Build spec and prefix. They are the only workloads that can widen the measured gap, and the only ones that can close the argument that steady is simply too gentle.
  2. Build PimAware — and hold it to the right bar. Beat 1173 GB/s without contiguous allocation's 9,162 admission failures. If it cannot, that is the finding.
  3. Settle the framing. The block-size result is the stronger claim the data supports; the allocator is the more interesting contribution. They may be the same result seen from two angles.

The thing worth keeping from Phase 0 is procedural rather than architectural: the stop rule fired, and we stopped. The number that came back was not the one the proposal wanted, and the two days spent building gates before results are what made it safe to say so out loud.
