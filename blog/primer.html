Rows and blocks

Everything you need to own the project — from what attention actually computes, to why a serving system's page allocator quietly destroys a DRAM accelerator's only advantage.

0x00

Where you're starting

You know GEMM, cache hierarchies, DRAM banks, and SIMT execution. You have not taken linear algebra and you have never worked with a transformer. That's a better starting position than it sounds, because attention is three GEMMs and a softmax — and the entire project lives in the memory behavior of those GEMMs, not in the math.

Nothing on this page needs eigenvalues, decompositions, or proofs. If you can reason about an M×N×K loop nest, its operand reuse, and its bytes moved, you can reason about every piece of this.

0x01

What the model is doing

A language model takes a sequence of tokens (integer IDs for word-pieces) and outputs a probability distribution over the next token. To generate text you sample one token, append it to the input, and run the whole model again.

That loop is autoregressive generation, and its serial dependency is the most important fact in this project. Token t+2 cannot be computed before token t+1 exists. Every technique below — KV caching, batching, paging, speculative decoding — exists to work around that chain or to make each link cheaper.

The layer stack

Llama-3-8B is 32 identical layers. Each has an attention block (the only place tokens interact with each other) and an MLP block (per-token, two big matmuls, no cross-token communication). The MLP holds most of the parameters. Attention holds all of the interesting memory behavior. We care about attention.

0x02

Attention, in GEMM terms

Each token produces three vectors by multiplying its embedding against three learned weight matrices: Q (query — what am I looking for), K (key — what do I offer to be found by), V (value — what do I contribute if found).

Attention is a soft dictionary lookup. Instead of matching one key exactly, you score your query against every key, normalize the scores so they sum to 1 (that's softmax — the only non-GEMM step, and it's cheap elementwise work), and return a weighted blend of all the values.

The three kernels

Move the phase toggle and watch M. In prefill, M is the whole prompt, so every byte of K and V you load gets reused across M rows of the output — a real GEMM, tensor cores fed, compute-bound.

In decode, M = 1. It's a GEMV. Zero reuse. Each byte of the KV cache is dragged out of DRAM, multiplied roughly twice, and thrown away. The tensor cores sit idle and the GPU is, in the most literal sense, a DRAM streaming engine.

Multi-head and GQA

Real models run many attention computations in parallel with different projections — heads. Llama-3-8B has 32 query heads of dimension 128. But K and V are the expensive things to store, so modern models share them: Grouped Query Attention gives Llama-3-8B only 8 KV heads, one per group of four query heads. A 4× cut in cache size, and it exists purely because of the problem in the next section.

0x03

The KV cache

Generating token t+1 needs K and V for tokens 1…t. Generating token t+2 needs the same set plus one. Recomputing them every step would be quadratic and pointless, so you compute each token's K and V once and keep them. Classic architecture trade: spend memory to save compute, then discover memory is now your whole problem.

Set it to Llama-3-8B defaults and read the first number: 128 KB per token. A 4,000-token conversation is half a gigabyte of cache. For one request. Thirty-two of them is 16 GB, on a card that also has to hold 16 GB of weights. The KV cache routinely exceeds the model itself.

Now look at the intensity number. Around 4 FLOP/byte with GQA, 1 with plain multi-head. A modern GPU's roofline ridge sits somewhere near 100–300. You are two orders of magnitude off the cliff. That gap is the entire argument for processing-in-memory: if the operation is "read a huge array and barely touch it," move the barely-touching to where the array already lives.

Why batching doesn't rescue you

Batch 32 requests and the MLP weights get reused across all 32 — compute-bound again, problem solved there. But every request has its own KV cache. There is nothing to reuse across requests. Batching multiplies attention's memory traffic linearly. As batch size grows, attention becomes a larger share of decode time, not smaller.

0x04

Paging the cache

When a request arrives you know its prompt length and have no idea how long its output will be. Reserve the maximum and you waste most of it — measured at only 20–38% of reserved KV memory actually used in pre-vLLM systems. Requests also arrive and finish at different sizes, so free memory becomes swiss cheese. Textbook external fragmentation.

vLLM's fix is one you already know cold, which is why this section is short: apply OS virtual memory paging to the KV cache.

Waste drops from 60–80% to under 4%, and prefix sharing falls out free: fifty requests with the same system prompt point their block tables at the same physical blocks. It is a genuinely excellent piece of systems engineering.

What it costs

The attention kernel can no longer assume K and V are contiguous — it gathers through the block table. Measured overhead (vAttention): paged prefill kernels up to 37% and 42% slower than non-paged in FlashAttention-2 and FlashInfer, 7–13% more instructions, extra register pressure and spills. And the paged decode kernel is sensitive to block size, degrading at 64 and 128 because of L1 efficiency.

That last point is the tell. Block size is already known to be a hardware-sensitive parameter, tuned by measuring GPU L1 behavior. Nobody has asked what it should be for DRAM.

Speculative decoding — your stress case

Decode is bandwidth-bound, so the GPU's compute sits idle. Speculative decoding exploits that: a small draft model proposes K tokens, the big target model verifies all K in one forward pass (nearly free, since you were bandwidth-bound anyway), and you accept the longest correct prefix. Output distribution provably unchanged. Tree drafting proposes a tree of candidates instead of one line.

What that does to the allocator is the point: every step allocates blocks along every branch, then frees all but one. Instead of appending one block every 16 tokens, you burst-allocate and burst-free several times per token. If paging scatters blocks under normal decode, speculation should shred it.

0x05

What PIM needs

Quick refresher, oriented at what matters here. A bank holds rows (~1 KB). ACT copies a row into the bank's row buffer. RD pulls columns from the open row, cheaply. PRE closes it. tRC — the ACT-to-ACT row cycle in one bank — is the expensive parameter. Sixteen banks per channel operate independently; that's your parallelism.

Put a small MAC unit next to each bank and you have PIM. Samsung's HBM-PIM and SK Hynix's AiM are real. The win is a bandwidth argument: a module's external pipe is maybe 64 GB/s, while the internal aggregate across all bank row buffers is tens of TB/s. Compute inside and you get the internal number.

The mechanism, which is the crux of everything: a PIM GEMV works by all-bank operation. Activate the same row index in every bank at once, broadcast one input vector to all bank MAC units, let each multiply against its own row buffer, and send only the tiny partial sums back out. Speedup ≈ the bank count.

The condition nobody writes on the tin: step one requires the operand data to actually live at the same row index across all 16 banks. If it doesn't, you cannot issue an all-bank command. The advantage evaporates entirely — not gradually.

The published finding this project builds on

Someone extended the AttAcc simulator with Ramulator 2 and measured PIM decode GEMV properly. Result: tRC is 10–11× larger than nCCDAB, the power-constraint parameter prior work had been optimizing. So nCCDAB is entirely masked and those optimizations do nothing for decode. The root cause: host-centric address interleaving forces every all-bank MAC command into a different DRAM row.

Address mapping is the piece most people skip. A physical address doesn't map to DRAM structure naturally — the controller slices address bits into channel / bank-group / bank / row / column fields, and that slicing is tuned for CPU and GPU streaming patterns. It was never designed for a bank-parallel compute unit.

And note the assumption in that finding: static placement, chosen once by the architect. That's the best case.

0x06

The collision — this is the project

PIM requires operand data at the same row index across all banks. Paged serving delivers 16-token blocks scattered across a pool by a runtime free list, allocated and freed out of order, shared across prefixes, laid out for GPU coalescing.

The incompatibility has three layers, and being precise about which is which is what turns this from a vibe into a project.

  1. Intra-block tensor layout. vLLM stores K blocks in a layout tuned so a warp's 32 threads produce one coalesced 128-byte transaction. Optimal for SIMT gather. Not what a bank-parallel MAC unit wants.
  2. Block ID → physical address. Even with a perfect intra-block layout, host-centric interleaving scatters a block's bytes across channels and rows. This is the published finding above, and it applies to us directly.
  3. Inter-block placement — the new part. Even with layers 1 and 2 fixed, a decode step must stream every block of the sequence. Those blocks sit wherever the free list put them: non-adjacent, arbitrary order, interleaved with other requests, fragmented further by prefix sharing and speculative churn. Every block boundary is a potential row cycle.

Nobody has measured layer 3. The PIM papers assume static placement, so it never comes up. The serving papers assume flat memory, so it never comes up. That gap is the project.

Work the numbers yourself

Don't take the magnitude on faith — this arithmetic is Phase 0. For Llama-3-8B, one layer, K only: 8 kv_heads × 128 head_dim × 2 B = 2 KB per token, so a 16-token block is 32 KB. For an HBM3-PIM geometry, one all-bank row activation covers 16 banks × 1 KB = 16 KB. So a block is exactly two all-bank row-sets — if it's aligned and if the address map cooperates. Neither is guaranteed by anything in the serving stack. Then ask:

  • Where does block N actually start in physical address space, and is that a multiple of 16 KB?
  • After a host-centric interleaving function, do those 32 KB even land in one channel?
  • For a 2,000-token context you stream 125 blocks. What's the row-hit rate across block boundaries at arbitrary indices?
  • What does all of that look like after 10,000 requests have arrived and departed?

Why the fix belongs in the allocator

You could fix this with new PIM hardware (expensive, unbuildable in two weeks, and it's adding silicon to solve a software layout problem) or a new attention kernel (helps layer 1 only, and the kernel doesn't control physical placement). Or you fix the allocator, which is already deciding placement and is just deciding badly, because nothing ever told it placement had physical consequences.

Bank-group-aligned pools, block size derived from row geometry instead of tuned on a GPU, alignment-preserving reuse on free. Same abstraction, same API, same capacity efficiency, different physical outcome. And a clean recommendation at the end: the serving community converged on block_size = 16 by measuring GPU L1 behavior; here is what it should be on a PIM-backed system, and here's the derivation.

What would kill it. If vLLM's LIFO free list already returns blocks in near-sequential order under steady load, physical placement might be fine and layer 3 doesn't exist. Layers 1 and 2 would still be real, but they're published, and you'd be re-deriving someone else's result. That's why Phase 0 is a two-day kill test and not an afterthought. If the baseline comes back high, say so and pivot — don't go hunting for a workload that makes the number look bad.
0x07

Check yourself

You own this when you can answer these without looking. Try each one out loud before opening it.

Why does generating token 500 require reading K and V for tokens 1–499, but not their Q?

Q is the thing doing the looking, and only the current token is looking. K and V are what gets looked at, so every past token's K and V stay relevant forever. That asymmetry is exactly why the cache is called a KV cache.

Why does GQA cut Llama-3-8B's cache 4×, and what does it cost?

32 query heads share 8 KV heads, so you store 8 sets of K and V instead of 32. The cost is expressiveness — grouped query heads are forced to attend using the same keys and values, which is a small quality hit the models are trained to absorb.

Why does batching help the MLP but not attention?

MLP weights are shared by every request, so batching amortizes one weight load across N tokens. KV caches are per-request and shared by nobody, so batching multiplies that traffic instead of amortizing it.

Give the arithmetic-intensity argument for decode being bandwidth-bound.

Per layer per token you read 2 × kv_heads × head_dim × dtype bytes and do about 4 × q_heads × head_dim FLOPs, which reduces to 2 × q_heads / (kv_heads × dtype) FLOP per byte — 4 for GQA-8 in FP16. The GPU's ridge point is 100–300. You're two orders of magnitude below it, so you're pinned to the bandwidth roof.

What does an all-bank PIM command require of the data layout, and what happens when it isn't met?

The operands must sit at the same row index in every bank of the channel, so one ACT and one broadcast column command serve all banks. If they don't, you can't issue the all-bank command at all — you fall back to per-bank operation and pay a full tRC per row. The loss is a cliff, not a slope.

Why is tRC the relevant timing parameter for PIM decode rather than nCCDAB?

Because the address map forces consecutive all-bank MACs into different rows, so you're paying activations, not hitting the column-command rate limit. tRC is 10–11× larger, which masks nCCDAB entirely — and means every optimization aimed at the smaller parameter does nothing.

Name the three layers of the paging/PIM mismatch, and which is already published.

Intra-block tensor layout; block-ID-to-physical-address mapping; inter-block placement by the allocator. The middle one is published — that's the AttAcc/Ramulator 2 finding. The third is the open one, and it's yours.

What single measurement would falsify the project, and what value would it need?

Baseline PIM row-hit rate under a realistic paged allocator trace. If it comes back high — say above ~0.7 — the placement problem doesn't exist at layer 3 and the premise is dead. That's Phase 0, and it runs before the proposal is locked.
