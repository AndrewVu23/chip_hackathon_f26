Paged for Capacity, Punished by Rows

Processing-in-memory accelerators make LLM decoding fast by computing inside DRAM — but only if the KV cache is laid out in aligned rows. The allocator that made LLM serving memory-efficient guarantees it isn't. Here is what that costs, and how to get it back.

01The short version

Generating one token from an LLM means reading the model's entire memory of the conversation and doing very little arithmetic with it. That makes decoding a bandwidth problem, not a math problem.

A promising fix is to stop moving the data at all: put small multiplier units inside the DRAM chips themselves and compute where the data already lives. Several published designs do exactly this. All of them depend on one hardware trick — activating the same row in every memory bank at once, then issuing a single command that makes all sixteen banks compute in parallel.

That trick has a precondition: the data must physically sit at the same row index across all those banks. And the allocator every modern LLM server uses — PagedAttention, from vLLM — guarantees it does not. It hands out fixed-size blocks from a free list, wherever a block happens to be available.

We built a simulator that replays realistic serving traffic through a faithful copy of vLLM's allocation policy, maps the resulting block addresses onto real DRAM geometry, and measures what an in-memory accelerator would actually achieve. The answer: today's allocator leaves roughly half the available bandwidth on the floor. A block allocator that understands DRAM rows recovers essentially all of it, at every block size, with no extra memory.

02Two good ideas that don't fit together

Why in-memory computing wins

DRAM is organised into banks, and each bank into rows. To read anything, the chip first activates a row — copying it into a small buffer — and that activation is slow. Reading more data from an already-open row is fast; switching rows is expensive.

An in-memory accelerator exploits this with all-bank operation. It opens the same row number in all sixteen banks of a channel simultaneously, then broadcasts one command. Every bank multiplies its own slice of data at the same time, so one command does sixteen banks' worth of work.

The catch is in the words "the same row number". If the data you need in bank 0 is at row 900 but the data in bank 1 is at row 41, you cannot do this. You fall back to opening rows one at a time and pay the slow activation over and over.

Why paging exists, and why it scatters

PagedAttention solved a genuine problem. Before it, a server reserved enough contiguous memory for each request's worst-case length, and wasted most of it. Paging splits the cache into fixed 16-token blocks, hands them out on demand from a free list, and lets different requests share blocks. Memory waste dropped dramatically. It is the right design — for capacity.

But blocks land wherever the free list happens to point. Sequences arrive, grow, finish, and return their blocks in whatever order they finish; the next request picks up those scraps. After a few minutes of real traffic the physical layout is confetti.

The arithmetic that sets up the whole problem

On the HBM3-class geometry we model, one row index across all 16 banks of a channel holds 16 KB. A 16-token block, spread over the 32 channels, contributes only 2 KB to each one — one-eighth of a row-group. So eight consecutive blocks have to land adjacently before the accelerator gets one clean all-bank operation. Nothing in the allocator arranges that.

03How we measured it

We deliberately did not run a language model. Nothing about this problem depends on what the model says — only on when blocks are allocated and freed. So we built a harness that isolates exactly that, and runs on a laptop in minutes with no GPU.

Four pieces

A workload generator produces realistic request streams: steady chat-like traffic with long-tailed lengths, long-context requests, requests sharing a common system prompt, and tree-style speculative decoding, which forks and discards branches several times per token.

A faithful copy of vLLM's allocator. Rather than install a serving stack, we ported the allocation policy from vLLM's block manager — the free list, the block table, reference counting, copy-on-write on fork. It reproduces the real ordering behaviour, including the detail that vLLM's free list is last-in-first-out.

An address map turns each block's bytes into physical DRAM coordinates — channel, bank group, bank, row, column — under configurable interleaving schemes, so we can ask what different memory controllers would do with the same allocation decisions.

A model of all-bank execution walks a sequence's cache in order, groups the reads into all-bank commands, and reports four numbers: how often a command finds its row already open, how many banks actually participate, the resulting effective bandwidth, and the decode latency that implies.

Guardrails

Five checks run as tests on every change, and no number gets reported unless they pass. Two are anchors with known answers: a perfect contiguous layout must score near the theoretical ceiling, and a randomly scattered layout must score near the theoretical floor. The others enforce that results improve monotonically with block size, that identical seeds give byte-identical output, and that every block allocated is eventually accounted for. The suite is 85 tests.

04What we found

The layout is worse than "imperfect"

Before any DRAM modelling at all, you can just look at where blocks land. Under steady traffic with standard 16-token blocks, only 6.9% of a sequence's neighbouring blocks are physically next to each other, and each sequence is smeared across 5.4× more alignment regions than its size requires. The PIM-aware allocator puts 92% of neighbours adjacent and uses exactly the minimum number of regions — a spread factor of 1.00.

That comparison needs no timing model, no assumptions about the memory controller, and no debate. The layout modern serving produces is close to the worst case for this hardware.

Two levers reach the same place

At the standard 16-token block, the PIM-aware allocator raises the row-hit rate from 0.769 to 0.963 and effective bandwidth from 1,226 to 2,805 GB/s — 2.3×. At 4-token blocks the gap widens to 6.5×. Under speculative decoding it is 2.4×.

But notice where all three curves meet. At 128 tokens every allocator scores the same. That number is not tuned; it falls out of the hardware: row size × banks × channels ÷ bytes per token. A 128-token block is exactly one aligned region, so where you put it stops mattering.

So there are two ways to fix this, and they are worth stating separately because they cost different things. Use 128-token blocks and the problem disappears without touching the allocator — but you give up the fine-grained packing that made paging attractive. Or keep 16-token blocks and make the allocator alignment-aware — you keep the packing and get the same result.

The contiguous row deserves a note. Giving every sequence one unbroken span is the obvious way to get alignment, and it does work — but only if you buy the memory for it. At the pool size we run, it stalls admissions 3,343 times and finishes the same work 9% slower. Grow the pool to twice the mean demand and those stalls vanish entirely. That is the trade paging was invented to avoid, and the PIM-aware allocator sidesteps it: it matches the contiguous layout's alignment while allocating exactly as much memory as the paged baseline.

It's churn, not size

The long-context result is the one that reframes the problem. A 20,000-token prompt is allocated in a single burst at admission, and even a last-in-first-out free list hands out long adjacent runs when asked for hundreds of blocks at once. Those requests score 0.963 under the plain paged allocator — essentially perfect.

The damage comes from growth and turnover: sequences adding one block at a time while others finish and return theirs. So this is not a long-context problem. It is a busy-server problem, which is the condition production systems actually run in.

And it gets worse as models evolve

How much a block covers per channel depends on how many bytes each token stores, which depends on how many key/value heads the model has. Modern architectures have been cutting that number to save memory — from 32 heads down to 8 (grouped-query) and in some cases 1 (multi-query).

Each cut makes this problem worse, because a block's slice of each channel shrinks with it. On an older 32-head model the paged allocator is already nearly fine and the fix buys 1.2×. On today's 8-head models it buys 2.1×. On a 1-head model it buys 6.0×. The trend the field is following makes the mismatch more expensive, not less.

05Does the model hold up?

Everything above comes from our own analytical model of all-bank execution. That model could be wrong. So we checked it against two independent cycle-level DRAM simulators, replaying the same block layouts our allocators actually produced.

Row behaviour. Ramulator 2 is a standard DRAM simulator with its own memory controller and its own request reordering. Feeding it our address streams, its measured row-hit fraction lands within 0.003 of our predicted number for every sample — 0.795 against our 0.799 for paged, 0.963 against 0.964 for PIM-aware. The row-hit metric is not an artifact of how we chose to model things.

Bank parallelism. Stock DRAM simulators have no all-bank command, so they cannot test the second half of the model. The AttAcc project, an in-memory attention accelerator from ASPLOS 2024, publishes a Ramulator extension that does implement it — a real all-bank multiply-accumulate instruction. Its DRAM geometry matches ours exactly. We replayed our command streams through it as genuine all-bank instructions.

The test isolates bank parallelism cleanly: run identical sequences under two memory interleaving schemes, one that keeps banks usable and one that cripples them. Our model predicts the crippled layout needs 8.0× more all-bank commands for the same data. AttAcc measures 7.4× and 7.3× more cycles for the two well-aligned allocators. The bank-parallelism term is real and quantitatively close.

One calibration worth stating plainly

Our bandwidth figures assume a row miss costs a full row cycle with no overlap, using the published ratio of roughly 10.5. A real PIM controller overlaps activation with useful work, and AttAcc's measurements imply an effective ratio closer to 4.4. The consequence: our ratios are optimistic by about 1.4× on the row-miss component. On AttAcc's timing the 2.3× headline becomes roughly 1.6×. Every ordering, every crossover point, and every block-size conclusion is unchanged — but the honest headline number depends on which controller you assume.

06Where it doesn't help

A result is only useful if you know its edges. These are the conditions under which the gain shrinks or disappears, all measured rather than guessed.

  • When the memory pool is oversubscribedReal servers evict and recompute sequences under memory pressure. When we model that faithfully and squeeze the pool to 60% of demand, roughly 200 evictions occur and re-admitted sequences land in whatever fragments remain. The advantage falls from 2.1× to 1.38×. It never drops below the paged baseline, but the benefit clearly depends on having room to work in.
  • When the memory controller cannot reorderOur headline assumes the controller can reorder requests within a modest window — standard for real hardware. With reordering removed entirely, the gain narrows from 2.3× to 1.24×. The shape of every curve is identical; only the magnitude moves. The truth lies between these two bounds.
  • When contexts are longPrompts of 8,000 tokens and up are allocated in one burst and are already well laid out. The plain paged allocator reaches 0.963 there. If your traffic is dominated by long prompts and little turnover, this work buys you almost nothing.
  • When the model has many KV headsOlder multi-head architectures store enough bytes per token that a 16-token block nearly fills an aligned region on its own. The gain there is 1.2× — real, but not worth engineering effort.
  • What we did not simulateWe model vLLM's allocation policy rather than running vLLM, and we measure one representative transformer layer — block tables are shared across layers, so the placement pattern is identical in each. Absolute bandwidth figures remain analytical; the row-hit and bank-parallelism terms are both simulator-confirmed.

07What to do with this

The practical output is a block-size recommendation with a formula behind it, and an allocator design for teams who want to keep fine-grained paging.

Derive the block size, don't inherit it

16 tokens is a serving-side convention with no hardware meaning. For a PIM-backed system the right value is row size × banks × channels ÷ bytes per token — 128 tokens on the geometry here. At that size, placement stops mattering entirely.

Or make the allocator row-aware

Carve the pool into aligned regions, give each sequence its own, fill it in order, and return freed blocks to the region they came from. This reaches the same ceiling at any block size and costs no extra memory.

Keep speculative scratch separate

Speculative decoding allocates and discards draft branches constantly. Drawing those from a sequence's own region punches holes in it. Giving drafts their own scratch area keeps speculative traffic as fast as ordinary traffic.

Leave headroom

The benefit is largest when the pool is not oversubscribed. Below roughly 1× mean demand, eviction churn erodes alignment faster than any placement policy can restore it.

The broader point is about where this problem is best solved. The in-memory computing literature assumes a favourable data layout; the serving literature assumes memory is flat and placement is free. Each treats the other's hard part as someone else's concern. The measurements here suggest the cheapest place to reconcile them is the allocator — a few hundred lines, no hardware change, no extra memory, and no loss of the packing efficiency that made paging worth adopting.
